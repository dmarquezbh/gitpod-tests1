Um benchmark poliglota, na mesma máquina e no mesmo banco

17 implementações do mesmo conjunto de endpoints no estilo TechEmpower, sob o mesmo wrk, o mesmo PostgreSQL 16 e a mesma metodologia. O objetivo é comparar stacks e runtimes com o mesmo trabalho, incluindo o custo de RAM e o tamanho do artefato — não só req/s.

O que é medido

  • plaintext: Hello, World! com HTTP pipelining 16;
  • json: serialização por requisição;
  • db: um SELECT aleatório em world;
  • queries: N SELECTs aleatórios (q = 1, 5, 10, 20);
  • fortunes: SELECT + ordenação + HTML com escaping;
  • updates: N SELECTs + UPDATE em lote.

O servidor roda fixado em 2 CPUs (taskset 0-1) e o wrk em outras 2 (2-3), 10 s por nível, com primer e warmup. Níveis: 16/64/256/512 conexões no plaintext também 256/1024/4096 com pipeline 16. Host: Intel i5-3317U (2 núcleos, 4 threads, Ivy Bridge, sem AVX2), 3 GB RAM, Linux. PostgreSQL 16 em Docker, synchronous_commit=off.

A rodada do .NET 11

O .NET 11 platform saiu de ~14,3k req/s para 47,3k req/s em /queries?q=1 (2,8× o Rust axum) e de ~2,1k para 5,4k em q=20. O caminho foi:

  • uma consulta por request: unnest($1::int[]) WITH ORDINALITY substituiu N Bind/Execute separados (q ≥ 2);
  • batching entre requests: todos os /db e /queries?q=1 vistos num ciclo de epoll viram um único SELECT com array (e um único Bind/Execute), com fallback escalar quando o lote tem 1 item;
  • updates em uma ida: o UPDATE com UNNEST deixou de ser precedido pelo SELECT (os valores novos são gerados no cliente);
  • driver libpq (C) via P/Invoke em todos os caminhos de banco, com arrays e pipeline mode: o parser linha-a-linha managed era o gargalo de fortunes e queries largas;
  • batching entre requests: todos os /queries de um chunk viram uma única consulta com os ids concatenados, e a tabela de fortunes é lida uma vez por rodada de epoll e distribuída aos requests pendentes;
  • runtime async do .NET 11 ligado no Kestrel e no platform; PGO dinâmico, workstation GC e ReadyToRun=0 mantidos;
  • Kestrel com Npgsql: mesmas consultas por array/UNNEST, q=10 de 3,1k → 6,4k, q=20 de 1,75k → 5,7k, updates q=20 de 1,27k → 3,2k.

Sobre “trocar o driver”: o cliente de wire protocol próprio continua mais rápido que o Npgsql neste host para o caminho de leitura; o ganho real veio de menos round-trips (array + batching por ciclo de epoll), não de trocar a biblioteca.

Zero C#

O Zero C#, fork do bflat que compila C# sem runtime nem GC, entrou com um servidor escrito só com DllImport (pthreads + epoll + libpq): 548k req/s no plaintext, 58 MB de RSS e 78 KB de binário (+354 KB de libpq). Sem runtime, sem coletor, sem async.

Caveats

  • Testes de banco são limitados pelo PostgreSQL deste host (2 núcleos); compare dentro da mesma rodada.
  • Java (HttpServer do JDK) acumulou erros de socket em níveis altos; Ruby usa WEBrick (thread por conexão); ambos são baselines honestos das bibliotecas padrão, não dos frameworks mais rápidos.
  • C++ entra com epoll + libpq (mesmo desenho do .NET platform): vence todas as categorias medidas, mas updates ficou de fora — UPDATEs UNNEST concorrentes geram deadlocks no PostgreSQL neste host.
  • GraalPy não fecha a conta neste host: o fallback de select() limita a ~1024 descritores (a rodada foi limitada a 256 conexões) e o processo chegou a 4,2 GB de RSS em 3 GB de RAM, com swap — os números são medidos, mas não representam o GraalPy em hardware adequado.
  • PyPy rodou a mesma app uvicorn e ficou abaixo do CPython 3.14: o JIT não compensa o custo de asyncio/threadpool neste workload, e o RSS foi ~650 MB contra ~220 MB do CPython.
  • As stacks do repositório rodaram numa sessão; as adicionadas, em sessões adjacentes, sem carga concorrente.
  • Portas remapeadas (18080–18094), Go em GOAMD64=v1 (CPU sem AVX2), DB em 127.0.0.1 no lugar do hostname tfb-database.
